## 三餐组合算法（核心）

**两阶段：餐位全枚举 Top-K + 日期间随机重组**

1. 阶段一：每个餐位（早30%/午40%/晚30%）枚举全部 (主餐, 小食, 饮品) 组合，允许分量为空（= 轻食餐位），按营养偏差评分取 Top-40。组合空间约 840，全枚举无压力。
2. 阶段二：400 轮重组——每轮按 `餐位分 + 全天去重惩罚(12/项) + 多样性扰动(0~6) + 预算软压力(8×溢出额)` 选组合，全天评分（热量100/蛋白60/脂肪25/钠10/预算12 权重）保留最优。

**实测性能**：约 80-200ms/次，误差见下。

## 调参过程中的领域发现（README 素材）

- **预算硬约束不可行**：麦当劳单品 ¥14-26，三餐 ¥100-130 是常态；预算必须做软约束并输出 `over_budget` 标记诚实告知。¥100 想吃满 1721kcal 物理上接近不可行。
- **蛋白缺口是真实痛点**：快餐蛋白密度低，1592kcal 减脂目标最多凑到 ~95g 蛋白（目标 126g），报告页应展示"蛋白缺口 + 补充建议"（纯牛奶/玉米杯是性价比之选）——这正好是产品的差异化叙事。
- **钠超标是普遍现象**：三个汉堡 ≈ 2800mg，超膳食指南 2000mg；报告页钠进度条是"劝退/劝换"的关键可视化。
- **早餐时段问题**：晚上调菜单无早餐品类，早餐餐位自动回退主食+轻食组合；正式使用时早上调用会拿到早餐菜单。
- 菜单与营养表名称对齐：归一化（全角括号/引号/™/空格）→ 全等 → 前缀 → 包含 + 规格偏好（中杯>小杯）；同营养项全天只挂一个菜单项。

## D2 补充：用券链路验证结果（2026-10-10 晚）

**已确认的服务端事实：**
1. `auto-bind-coupons` 领券成功 6 张（套餐券×3 / 免费脆薯饼 / 麦旋风买一送一 / 9.9元冰美式）；券 ID **只在领券结果中返回**，`query-my-coupons` 仅返回标题/价格/有效期/标签（卡包显示 5 张，免费脆薯饼不在列）。
2. `calculate-price` 用券必须 **couponId + couponCode 成对传**，缺任一报 600010。
3. 成对传入后，全部组合报 **600012（当前优惠券不可用/未找到券）**——含券对应商品（脆薯饼/麦旋风×2/美式）、换 SKU、换数量均失败。

**结论与决策：**
- 券存在隐性使用条件（可能是：指定门店类型、时段白名单、指定 SKU 之外的限制，或这些营销券只支持 create-order 时核销而非算价阶段）。
- 代码侧 `best_price_with_coupons` 采用**容错试算**：单组合失败自动跳过并回退无券原价，主流程不受影响；`--bind` 开关显式控制领券副作用。
- **开放问题（进 GitHub Issues）**：① 券核销的真实触发条件；② 券与商品的映射获取方式；③ 套餐券 10-11 生效，次日可再验证时段因素。
- 已领的券在麦当劳 App 内正常可见可用，不影响用户权益。

**D2 验收：算价主链路（无券）✅ 完整可用；用券链路代码就绪、真实验证待条件明确。**

# D3 开发笔记：可视化营养报告页（2026-10-10 晚）

## 交付
- `src/report.py`：报告生成器——Chart.js 雷达图（五维达成率，钠为反向指标）+ 三餐热量环形图 + 四项营养进度条（绿/橙/红三态）+ 钠超标/蛋白缺口/预算三类洞察文案 + 门店与官方算价展示。1080px 分享卡片版式，麦当劳品牌黄渐变头部。
- `src/main.py` 新增 `--report [路径]`：规划完成后一键生成报告 HTML，结果 JSON 补齐 `profile` 字段。

## 设计决策
- **雷达图钠维度做反向换算**（上限/实际×100），超标时数值 <100，雷达自然内凹，比直接展示 mg 更直观。
- **进度条三态语义**：热量/蛋白 80-120% 绿、低于 80% 橙（缺口）、高于 120% 红；钠 ≤100% 绿、超标红——与「营养师点评」文案联动。
- **洞察即卖点**：蛋白缺口给出纯牛奶补齐建议、钠超标给次日选品建议，这是 README 里"诚实展示快餐营养现实"差异化叙事的报告端落地。

## 验证
- demo-input.json（e2e 门店+官方算价 ¥114.5 + profile）→ demo-report.html，8 项内容校验全过、无模板占位符残留。
